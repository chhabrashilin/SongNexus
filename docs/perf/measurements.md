# Performance measurements

Plan §23 budgets are proposals until measured. Actuals are recorded here; targets are never edited after the fact.
Measured on a developer laptop (Windows 11, Python 3.12, single process), reference catalog of 5,854 artists,
23,800 search keys. Staging numbers on Cloud Run (1 vCPU) are still to be taken (M8-01).

## 2026-10-07

| Budget (plan §23) | Target | Measured | Status |
|---|---|---|---|
| p95 SearchCatalog | ≤ 50 ms | p50 9 ms, p95 14–19 ms, max 36 ms (600 mixed queries: prefixes, full names, typos) | Met |
| AnalyzePlaylist, graph analysis (2,000 artists) | — | 10 ms | — |
| p95 AnalyzePlaylist (2,000 artists) | ≤ 1.5 s | ~13 s cold, dominated by name matching (~6.5 ms per distinct name); typical playlists (50–150 artists) 0.3–1 s | **Missed at the 2,000-artist maximum** |
| Read model load | — | 1.0 s | — |
| Web initial JS | ≤ 200 KB gzip | 129.4 KB | Met |

### Name matching: what was tried

| Change | 2,000 names | Search p95 | Kept |
|---|---|---|---|
| Baseline: one ranked search per name | 62 s | 71 ms | — |
| Edit-distance bound in pure Python | 93 s (worse) | 71 ms | No |
| Native edit distance (rapidfuzz OSA; verified equal to the reference on 1,000 cases) | 24 s | 18 ms | Yes |
| Trigram sets cached, partial ranking, type pre-filter | 24 s | 14 ms | Yes |
| Exhaustive filtered candidates at the review floor (0.69) | 110 s (worse: the q-gram bound is vacuous at 31% error) | — | No |
| Exhaustive filtered candidates at the decision floor (0.80) | 13 s | 14–19 ms | Yes |
| Prefix filtering on rare trigrams | 15 s (no gain: 89% of trigrams still probed) | — | No |

The kept design is exact for every matched/not-matched decision (property-tested against brute force); see
`SearchIndex.similar_docs` and `decisive_similarity`.

### Mitigations for the missed budget (in R1)
- Resolutions are cached per catalog version (`ResolutionCache`), so popular artists are matched once across users.
- History imports match the 500 most-listened artists, not every artist ever played.
- The UI shows progress; the request is a single call per playlist.

### Path to the target (R2)
Precompute resolutions for every catalog name and alias at ingest time (an exact-key lookup then decides most
real-world names in microseconds), and move fuzzy candidate generation to a native index. Re-measure on Cloud Run.

## Import match quality (AC-10.2)
Labeled set `data/eval/import_match_cases.json` (395 cases, generated by rules from human-verified seed IDs):
precision **0.993** (gate ≥ 0.98), recall 0.907. Homonyms auto-matched: 0 of 22. Both errors are labeled near
misses: "The Beetles" → The Beatles and "The Weekend" → The Weeknd, the inherent cost of typo tolerance.

## 2026-10-13: Load test (M8-01), local

`server/scripts/load_test.py`: closed-loop, six read scenarios over 27 discovered artists, one uvicorn process,
SQLite, load generator on the same laptop (so the two compete for CPU), rate limits raised. 8 s per scenario, 0 errors
in every run.

| Scenario (budget) | 1 client p50 / p95 | 8 clients p50 / p95 | 8 clients rps | Status |
|---|---|---|---|---|
| SearchCatalog (p95 ≤ 50 ms) | 6.4 / 12.5 ms | 43 / 95 ms | 161 | Met at 1 client; **missed at 8** (queueing on one worker) |
| GetArtist (≤ 100 ms) | 5.6 / 10.7 ms | 30 / 126 ms | 175 | Met at 1; **missed at 8** |
| ListCollaborations (≤ 100 ms) | 3.9 / 8.2 ms | 26 / 96 ms | 220 | Met |
| FindPath (≤ 150 ms) | 10.5 / 27 ms | 29 / 101 ms | 200 | Met |
| CompareArtists (≤ 150 ms) | 5.8 / 15.7 ms | 38 / 118 ms | 163 | Met |
| GetPuzzle | 3.8 / 12.4 ms | 91 / 149 ms (p99 1.4 s) | 55 | No budget; p99 outlier, see below |

Reading the results:
- Service time is a few milliseconds; the 8-client numbers are queueing behind one Python worker. A single instance
  saturates near 160–300 requests/s. Cloud Run adds instances (and the production database is not SQLite), so the
  budgets must be re-measured there (still open, needs a GCP project) with the load generator on another host.
- An earlier 8-client run showed a 3× slower GetArtist; an immediate re-run did not reproduce it (machine noise).
  Both are kept here rather than choosing the better one.
- GetPuzzle's p99 outlier is the first request after the process starts computing the puzzle pairs once
  (`ReadModel.memo`); the cost is paid once per catalog version. Warming it at startup is a cheap R1 follow-up.
- The load test found no errors, no memory growth worth noting, and no endpoint above budget at one client.
- Finding fixed while writing the test: puzzle and path methods use the stricter "analyze" rate limit (120/min per
  client); that is intended, and the script documents raising the limits for measurement.

## 2026-10-21: AnalyzePlaylist name matching, second pass

Profiling showed the time was not edit distance but Python overhead in `SearchIndex.similar_docs`: counting shared
trigrams per candidate key in a Python loop and scanning song and release keys for artist queries. Two exact changes:

1. Posting lists and length buckets are kept per entity type, so an artist query never touches recording or release keys;
   shared-trigram counts are computed in C (`Counter` over chained lists).
2. The smallest shared-trigram count any qualifying key can have is computed once per query, and keys below it are
   dropped before any per-key work. It is derived from the same bounds as before, so completeness is unchanged.

Decisions are identical (same digest over mention, decision and entity ID for all 2,000 names; import precision 0.993
and recall 0.907 unchanged; the brute-force completeness property test passes, with a new mixed-entity-type variant; a
deliberately tightened bound is caught by that test).

| Measure (`server/scripts/bench_resolve.py`: 2,000 names, 40 % exact, 25 % one typo, 15 % article changes, 20 % absent) | Before | After |
|---|---|---|
| `resolve_batch`, single thread | 4.46 s (2.2 ms each) | **1.33 s (0.66 ms each)** |

End to end through the API (`POST /v1/playlists:analyze`, 2,000 distinct names, same laptop and process as the load
test, SQLite): first (cold) request **1.11 s**, later requests 0.6–0.8 s once names are in the resolution cache;
150-name playlists 0.08–0.10 s.

Status of the plan §23 budget (p95 ≤ 1.5 s at 2,000 artists): **met on this laptop**, with little headroom. This laptop
has far faster cores than a 1 vCPU Cloud Run instance, so it is **still unverified where it matters** and the R2 design
(precomputed resolutions, native candidate index) stays documented. The earlier "13 s" figure used a harder name mix
and an earlier code state; the 4.46 s "before" above is the same mix as the "after", for a like-for-like comparison.

## 2026-11-04: Explore frame rate with a large web (R2-2)

Budget (plan R2-2): Explore at ≥ 50 fps with 300 artists on a mid-range phone. Method: `e2e/perf.spec.ts`
(opt-in, `SONGNEXUS_PERF=1 npx playwright test perf --project=mobile`), Pixel 7 emulation, the web grown to the
300-artist cap with "Expand the 5 strongest", frames counted with `requestAnimationFrame` over 2.5 s. "Moving" is
measured right after a change restarts the layout; "settled" after the layout stops. CPU slowdown 4× is Chrome's
mid-tier-mobile preset.

Finding first: headless Chromium rasterizes canvas in **software** by default; a profile showed 66–90 % of the time
in native raster, not in our code. Numbers below use the GPU (`--enable-gpu`); software-raster numbers are not
representative of a phone and are not reported as results.

Changes made: lines that look alike are stroked as one path; ordinary nodes are one fill and one stroke; the canvas
draws at 1× while the layout is moving and at up to 2× once settled; label halos are skipped while moving. At 81
artists and 4× slowdown (software raster) this alone took the moving web from 11–17 fps to 34–36 fps.

| 300 artists, GPU on | Runs (5) | Median |
|---|---|---|
| Moving, normal CPU | 59.5, 13.1, 60.2, 3.2, 60.3 | **59.5 fps** |
| Moving, 4× CPU slowdown | 22.4, 41.4, 8.7, 37.1, 0.2 | **22.4 fps** |
| Settled, 4× CPU slowdown | 60.7, 59.2, 60.5, 60.2, 60.1 | **60.2 fps** |

Runs are noisy on this shared laptop: the outliers (0.2, 3.2) are a single frame stalled for seconds, which a
profile could not attribute to our code. A static page in the same setup reads 47–57 fps at 4×, which bounds what
the harness can show.

Status: **met for a settled web and for a moving web on a fast CPU; unverified for a moving 300-artist web on a
mid-range phone** (22 fps median in emulation). The remaining step is measuring on a real mid-range Android phone;
if it confirms the emulation, the next lever is warming the layout up off-screen (running the first ticks without
drawing), which shortens the moving phase rather than speeding it up.

What the numbers say, honestly:

- The first request for a URL is unchanged by design (a cache cannot speed up a first computation; cold figures
  differ only by machine noise). Warm repeats, which is what a popular artist, a shared link or a Home load sees,
  drop to the 4-8 ms loopback floor, and the expensive analyses fall furthest: strongest-links paths 42 to 6 ms
  p50 (290 to 7 ms p95), recording comparison 24 to 6 ms.
- A conditional request (`If-None-Match`) is answered 304 with no body: 4 ms on `/v1/genres`.
- Responses over 1 KB are gzip-compressed (3-6x smaller on the wire for the large lists).
- `GET /v1/artists:featured` replaces 12 `catalog:search` calls on every Home load: cold 128 ms once, then 7.5 ms,
  and the browser keeps it for 30 minutes.
- Browser side: catalog queries stay fresh 30 minutes (they change only with `graphVersion`; sign-in, sign-out and
  blocking invalidate them), and hovering or focusing an artist link for 120 ms prefetches that artist page.

Not measured here: multi-instance behavior with Redis and Cloud Run numbers (still open, as above).

### How caching is layered

| Layer | What | Lifetime |
|---|---|---|
| Browser (TanStack Query) | catalog queries | 30 min fresh, 60 min in memory |
| HTTP (`Cache-Control`, `ETag`) | anonymous catalog GETs: `public, max-age=60, stale-while-revalidate=600`; the ETag hashes `graphVersion`, method and URL | 1 min, then revalidated with 304s |
| Server response cache | serialized JSON of anonymous catalog reads, keyed by `graphVersion` and the full URL; concurrent misses are computed once | 1 h TTL, LRU, 4,096 entries / 64 MB |
| Redis (optional) | the same entries, shared by instances | 1 h TTL |

Anything for a signed-in viewer (a blocked-artist filter changes results), plus `/v1/users`, sessions, shares,
accounts and any response that sets a cookie, is `private, no-store` and never enters a shared cache.

### Turning on Redis in production (for example Memorystore on Cloud Run)

Redis is optional; one instance already gets most of the benefit from the in-process cache. It helps when several
instances would otherwise each warm their own copy (Cloud Run scale-out, cold starts).

1. Create a Memorystore for Redis instance (Basic tier is enough: a cache may be lost) in the same region and
   VPC as the service. Use `maxmemory-policy allkeys-lru`.
2. Give Cloud Run VPC access (Direct VPC egress or a Serverless VPC Access connector) to that network.
3. Install the extra in the image (`uv sync --extra redis`) and set
   `SONGNEXUS_REDIS_URL=redis://<memorystore-ip>:6379/0` (use `rediss://` plus a secret-managed password if AUTH or
   in-transit encryption is on).
4. If Redis is unreachable, the API logs one warning, serves from memory, and retries every 30 seconds; it never
   fails a request because of the cache. Keys contain the catalog version, so a data refresh needs no flush.
5. Locally: `docker compose --profile cache up -d`, then `SONGNEXUS_REDIS_URL=redis://127.0.0.1:16379/0`.

Hit and miss counters are on `ResponseCache.stats()`, and every cached response carries `X-Cache: hit|miss`.
