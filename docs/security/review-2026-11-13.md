# Security review: Release 2 (R2-8)

Scope: what R2 added on branch `r2` as of 2026-11-13: linked listening accounts (OAuth, token storage, outbound
provider calls, the sync job), development sign-in, and friends and sharing. The [R1 review](review-2026-10-13.md)
still covers everything else. Method: a STRIDE walk against the code and its tests. This is not an external
penetration test, and nothing was tried against real provider apps (no keys are configured).

## Linked accounts (ADR 0006)

| Threat | Control | Evidence | Status |
|---|---|---|---|
| Stolen tokens from the database | AES-256-GCM with a key outside the database (Secret Manager/KMS in production, a local key file in development); key ID prefix for rotation; the user and provider are bound as associated data, so a ciphertext copied to another row fails to decrypt | `test_tokens_are_encrypted_bound_to_their_account_and_rotatable` | Pass |
| Tokens leaking through the API, logs or export | tokens are never returned, logged or exported | `test_export_includes_links_and_tallies_but_never_tokens`; log assertions | Pass |
| OAuth CSRF and login fixation (attacker links their account to the victim) | `state` is random, stored only hashed, single use, expires in 10 minutes and is bound to the session that started the flow; PKCE (S256) for Spotify and Google | `test_a_link_started_in_one_session_cannot_be_finished_in_another`, `test_spotify_links_with_pkce_and_state_then_syncs` (replay rejected) | Pass |
| Open redirect via the callback | redirect URIs are built from `SONGNEXUS_APP_ORIGIN`, never from the request; the callback only redirects into the app with `?linked=` or `?linkError=` | code review; `test_declining_on_the_provider_returns_to_the_app` | Pass |
| SSRF through provider URLs | provider base URLs come from configuration only; nothing user-supplied is fetched | code review (`accounts/connectors.py`) | Pass |
| Forged ownership (linking someone else's ListenBrainz or Last.fm) | ListenBrainz tokens are validated with `validate-token`; Last.fm needs the signed `auth.getSession` exchange | `test_a_rejected_token_does_not_link`, `test_lastfm_links_with_a_signed_session_exchange` | Pass |
| Provider abuse or ban from aggressive polling | sync every 15 minutes, exponential backoff to 24 h on failure, "Sync now" at most once a minute per account, a fixed amount of history fetched per run | `test_a_provider_outage_backs_off_and_keeps_the_link`, `test_sync_now_is_limited_to_once_a_minute` | Pass |
| Revoked access treated as an outage | 401/403 from a provider marks the link NEEDS_RELINK and stops syncing it | `test_a_revoked_link_asks_to_relink_and_relinking_keeps_history` | Pass |

## Development sign-in

`POST /v1/sessions:local` signs in without an identity provider. It exists only when `environment=development` and
no Firebase project is configured, and `validate_for_serving` refuses to start any other environment without a
Firebase project, so it cannot be on in a deployed service (`test_local_sign_in_exists_only_in_development_without_firebase`).
The development token key is generated into `data/raw/local/` (gitignored) and is never used outside development.

## Friends and sharing (ADR 0007)

| Threat | Control | Evidence | Status |
|---|---|---|---|
| Unwanted contact | no search, contacts or directory; friendship only by an invite the other person chose to send | design; `test_sharing_needs_a_friendship` | Pass |
| Guessing invite codes | 50 random bits from `secrets`; single use; 7-day expiry; preview and accept need sign-in and are rate-limited per user | `test_an_invite_makes_two_people_friends_and_is_single_use`, `test_invites_expire_after_seven_days` | Pass |
| Codes leaking from the database or export | only SHA-256 is stored; the list and export never show codes | same test; `test_export_covers_friends_and_sharing_without_codes` | Pass |
| Learning that you were blocked | invites, previews and shares across a block fail exactly like expired invites or non-friends | `test_blocking_is_silent_and_mutual` | Pass |
| IDOR on inboxes, friends and shares | every user resource is resolved through `authorize_user`; shares are reachable only by their sender and recipient | `test_friends_need_sign_in_and_stay_private`, `test_recipients_and_senders_can_remove_shares` | Pass |
| CSRF on social writes | the same Origin plus `X-CSRF-Token` check as every user write | shared `check_write_origin`; the R1 CSRF tests cover the mechanism | Pass |
| Spam and phishing in notes and names | rule moderator rejects links and hidden or bidi-control characters; 140-character notes; 20 shares an hour and 100 a day per sender, counted in the database | `test_notes_are_moderated_and_limited`, `test_display_names_are_moderated_and_tidied`, `test_senders_are_rate_limited` | Pass |
| Stored XSS through notes or names | React renders text only (no HTML injection anywhere in the app); the strict CSP is the second layer | code review; `csp.spec.ts` | Pass |
| Abuse with no recourse | block and report on every share and friend; reports keep a copy of the note for moderators for 90 days | `test_reporting_a_share_keeps_a_copy_and_clears_it` | Pass |
| Repudiation | audit entries for every social change (`friend.add` for both people, `share.create`, `userBlock.create`, `report.create`, …) | `test_export_covers_friends_and_sharing_without_codes` | Pass |

## Findings and decisions

| # | Finding | Severity | Decision |
|---|---|---|---|
| R1 | Closing the age dialog after a confirm cancelled the new session, so first sign-in looked like it failed (Google and local). Found while testing in the browser. | Medium (broken sign-in, no security impact) | Fixed in e8b1e20; `AuthProvider.test.tsx` fails without the fix. |
| R2 | The moderator is rule-based only; harassment without links gets through. | Medium | Accepted for the reference build. Interface in place (`social/moderation.py`); wire a classifier before any public launch. Reports, blocks and send limits bound the harm. |
| R3 | No moderator console: reports are rows in `abuse_reports`. | Low | The [abuse runbook](../runbooks/abuse-reports.md) gives the queries. A console is product work. |
| R4 | Live OAuth against Spotify, Google and Last.fm is unverified (no developer apps configured here). | Medium | Verify on staging with real apps; the flows are covered by contract tests with every provider mocked. |
| R5 | The Spotify and Google redirect URIs must be registered exactly, per environment. | Low | Documented in `server/.env.example` and the [sync runbook](../runbooks/sync-failures.md). |
| R6 | Token key rotation is designed (key IDs) but there is no re-encryption job yet. | Low | Old keys stay configured for reading; add `songnexus rotate-token-key` before the first rotation. |

No critical or high findings. R2 and R4 gate a launch beyond testers, along with S4 and S6 from the R1 review.
